源码事实假设算例约 8 分钟 · 公式 + 可调窗口

MFU 的分母不是 world_size，分子也不是“所有 token”

DeepInfer 日志的 MFU 是：首尾样本之间、引擎排班的主模型 FP8 等价工作量，除以这段时间、model_parallel_size 与本机口径峰值。首条样本只定起点，不计工作量；时间不延伸到 now。这两个窗口细节决定了它不能和吞吐曲线混着读。

窗口内主模型估算 TFLOPs
分母
首尾时间 × MP × 峰值
MP
此仓 = CP，不是 EP / world
源码定义 stats_logger.py:203–209
MFU = Σi=1..n Fi ÷ (tn − t0) model_parallel_size × tflops_limit

Fi 是每步的 FP8 等价主模型估算 TFLOPs；t0 是首条样本的时间戳，F0 不计入求和；tn 是最后一条样本，不用当前时刻补尾。

model_parallel_size = context_parallel_size tflops_limit = get_bf16_tflops_limit() × 2

    def _mfu(self, now: float) -> float:
        entries = self._tflops.entries
        if len(entries) <= 1:
            return 0.0
        # 口径：首条仅作区间起点（值不计入），分母为首尾样本间隔、不延伸到 now（对比 _throughput；_tflops 每步都追加，实际末样本时间戳即 now）
        tflops_per_s = (sum(v for _, v, _ in entries) - entries[0][1]) / (entries[-1][0] - entries[0][0])
        return tflops_per_s / self._parallel_config.model_parallel_size / self._tflops_limit

逐段读 / 窗口与卡数

  1. L205–209首条样本只作起点。求和工作量时减去 entries[0][1]；如果只有一条样本，函数直接返回 0，不能凭一条记录算 MFU。
  2. 窗口分母是最后样本减首样本。它与 _throughput 的“延伸到 now”不同；前者是 MFU 窗口，后者是吞吐窗口，不能拿同一条曲线读。
  3. 卡数model_parallel_size 在这份 config 里等于 CP。把日志分母再按 EP 或全局 world_size 除一次，会重复或错配卡数。
  4. 峰值tflops_limit 是 bf16 参考峰值 × 2。它是 FP8 等价记账口径，不是本机实测峰值；硬件表由仓内参考值提供。
stats_logger.py:195–201 · throughput 窗口 llm_engine.py:304 · tflops_limit device.py:151–156 · 参考值不是实测

不要把首样本的 F 加回来。它是窗口起点的“零刻度”附近的记录；分子从一开始就排除了它。否则默认例子会从 200 变成 210 TFLOPs，MFU 也跟着错。

源码事实来自固定 SHA；短段用于逐行讲解，不复制完整文件。上游许可：Apache-2.0。

这个公式不能回答什么

它不能说明用户首 token 等了多久、相邻 token 多快，也不能说明设备是否被有用工作填满。它只回答：在一个首尾样本窗口里，按约定主模型等价 FLOPs、CP 与峰值口径，设备理论峰值被“记账工作量”用了多少。

无 GPU 实测；不展示虚构 MFU、吞吐或加速比。

想一想：为什么首条样本的时间戳要保留，但它的工作量不要？

分子是“从首样本之后到末样本”的增量工作量，需要首样本作窗口左端点；但 entries[0][1] 是起点记录，参考实现把它排除，避免把窗口外的第一步重复计入。两条规则一起定义了口径。

M13
口径对照约 5 分钟 · 三块仪表

GPU busy、MFU、吞吐：三块仪表，三个问题

设备有工作，不等于 Tensor Core 做了很多有用矩阵乘；MFU 高，不等于用户每秒收到更多有效 token；吞吐变好，也可能来自少做必做工作，而不是把设备用得更满。读性能数字前先问：它记的是设备活动、主模型记账，还是用户可见结果？

用户
TTFT、TBT、有效 token
设备01

GPU busy

设备时间轴上有 kernel、通信或拷贝在跑。它不保证这些工作都是有用的主模型矩阵乘，也不告诉你用户是否在等。

不能推出：MFU 高、吞吐高、延迟低。

约定口径02

MFU

按 FP8 等价记账的主模型工作量，除以首尾窗口、CP 与口径峰值。它是理论峰值的利用率，不是设备活动百分比。

不能推出：用户 token 速率、首 token 延迟、内容质量。

用户03

吞吐 / 延迟

用户每秒拿到多少有效 token，以及 TTFT、相邻 token 时间。少做必做工作可能提高吞吐，却不提高 MFU；推测解码多做的草稿计算也不计入这仓主模型分子。

不能推出：设备峰值利用率、单个 kernel 效率。

同一段墙钟时间 / 示意，不对应 trace三种问题
设备活动 有活，不代表都是有用 GEMM
主模型记账 只记约定 contractions；draft / pad / replicas 不计
用户可见 有效输出 token 与等待时间，不是设备字节数

条形长度仅为教学示意，没有任何毫秒或百分比含义；重叠的区域也不能重复计入总时间。

最常混的一步

把 GPU busy 百分比直接当 MFU，或把日志 MFU 乘上 world_size 当“整机效率”。前者换了分子，后者换了分母；两者都不再是 stats_logger 定义的量。若跨精度比较，还要先把 FP4/FP8/BF16/FP32 的记账系数统一。

分子只记主模型的 FP8 等价工作量

flops_estimator.hpp 估算主模型主要 contractions 的等价 FLOPs：GEMM 系数已包含乘加两次 FLOP。它排除 draft、padding 与 replicas，省略 norm/activation 小算术，vision 仍是 TODO；调度 q/k 也没有扣除 acceptance 或 ZOS 后续修正。因此它是“排班主模型工作量”的估算，不是最终接受 token 的实测 FLOPs。

逐项读 / 单位先对齐

  1. 分子TFLOPs 是工作量，不是 TFLOP/s。公式先除以时间得到速率，再除以并行大小与峰值，才变成无量纲的 MFU。
  2. attentiontotal 已含 attention。看到两个返回值时，不要把两者相加；这是读日志/改公式最容易犯的一次重复。
  3. 排除项draft、padding、replicas 不在这个分子里。这会让 MFU 与“设备总 FLOPs”或“用户有效 token”都不同；不要用一个替代另一个。
  4. 估算调度 q/k 未按 acceptance/ZOS 后续修正。所以分子更像“排班主模型工作量”，不是最终被接受 token 的实测。

这不是“越低精度越好”的证明。等价系数只是统一记账；精度、数值质量、硬件支持与真实 kernel 效率要另测。
