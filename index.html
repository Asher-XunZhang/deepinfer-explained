请求生命周期

一个请求从文本变成 token，进入 waiting 队列，被一轮轮调度、执行、采样，最终把已提交 token 返回给入口。

LLM→LLMEngine→Scheduler→Worker→ModelRunner→Sampler
谁决定
Scheduler 选择本轮 prefill / decode 批次。
谁执行
Worker、ModelRunner 与模型/kernel；KV 由 CacheEngine 承载。
代价视角
每轮多花在调度、下发、缓存搬运上的时间，未必能隐藏模型本身的计算。

03 / TERMS & SOURCES

术语先解释，
原件再下载。

一句话弄清本页反复出现的词；固定源码与官方结构快照放在同一处。结构快照只用于阅读，不是可运行的模型包。

术语一句话解释对应章节
Sequence一个请求的 token 历史、运行状态与 cache 账本；不是 GPU 里的 KV 字节本身。请求与调度
prefill / decode两种 step 类型：前者处理 prompt，后者逐 token 续写。调度器按预算与容量选择本轮步型。请求与调度
分块 prefill长 prompt 按本轮 token 预算分成多个 chunk；未完成前请求继续等待，最后一个 chunk 才提交首个输出 token。chunk 算例
block table / 分页 KV逻辑 token 位置经 block table 映射到不连续的物理块；CPU 账本分配编号，GPU 张量才真正保存字节。运行时与异步
SWA滑动窗口注意力只保留近窗上下文；本站在运行时页把主 KV、SWA state 与压缩 state 分开讲。KV 与 state
ZOS用跨步 remap 重叠 CPU 调度 / 后处理与设备执行；跨轮 event 依赖仍然要等待，不是“零成本”。ZOS
CUDA Graph捕获固定执行图后重放；按真实 q 行数选桶并补 padding 行，真实请求数另存给采样。Graph
DSpark / MTP草稿一次给出多个 token，目标模型验证连续接受前缀；首个拒绝后，从该位置用残差分布重采样。采样与结构
MoE / EPLBgate 选逻辑专家，EPLB 把副本映射到物理槽；dispatch / combine 必须把结果送回原 token 顺序。模型与并行
DP / CP / EP同一组 GPU 的三种分工视图：DP 分请求，CP 分同一序列的 query 行，EP 分 routed experts。并行边界
MFU模型 FLOPs 与硬件峰值算力、时间的比值口径；本站只解释公式与边界，没有 GPU 实测数字。测量与效率

把“开源实现”
和“生产系统”分开画。
