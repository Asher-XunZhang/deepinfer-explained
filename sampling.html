hidden 之后，先有候选空间，才有 token

模型最后一层给出 hidden states；采样位置上的 hidden 被投影成每个候选的 logit。logit 不是概率，也还不是 token。temperature、top-p、top-k 等 processor 改变候选空间，softmax 才把分数变成分布，最后才从分布里抽一个值。

逐层读 / 概率不是 token

  1. 对象hidden 是向量，logit 是每候选分数，p 是归一化质量，token 是离散编号。四者不能画成同一个框；把 logit 直接叫“概率”会掩盖 softmax 与 mask。
  2. 位置prefill 只取最后一个 prompt 位置的输出用于下一 token。decode 的采样位置随步推进；MTP 时还要先处理上一轮草稿验证。
  3. 顺序mask / top-p 在采样前生效。排除候选后，剩余候选的概率必须重新归一化，否则“总和为 1”不再成立。
  4. 随机固定种子不是全部条件。每请求 seed 在 SamplingParams 中，但 batch 行布局、MTP 与设备路径也会影响结果；条件见下一节。

本页不展示完整词表，也不复制 sampler 的函数体。交互图用 5 个候选呈现机制；真实实现面对更大的词表、mask 与按请求 seed。数值仅是教学算例。

性能作用与代价

采样不是“最后取最大值”那么轻：大词表上的 projection、top-k/top-p 的排序或阈值扫描、mask 的应用都要消耗工作；温度只是缩放 logits，不会减少模型主干的矩阵乘。把采样处理器做快，可能改善每步控制开销，但不能直接推导 MFU 或端到端吞吐收益。

源码因果，不是本机测量。没有采样耗时、词表大小或加速比数据。

想一想：top-p 排除候选后，为什么不能保留原来的概率值直接采样？

因为剩余候选的概率和已经小于 1。若不重新归一化，同一个 u 与区间边界的含义会变，采样结果不再是“在保留集合上的条件分布”。本图的 mask 后区间会伸缩，落点也可能改变。

草稿先跑，目标模型只收连续前缀

草稿模型一次猜出 A/B/C，不等于最终输出。目标模型在目标分布上验证这些位置；只保留从开头连续通过的 token。首个拒绝之后的位置全部作废，并在首拒绝位置用残差分布重新采样。若整段都通过，目标模型还要在末尾补一个正常采样 token，才能继续下一轮。

逐段读 / 只认连续前缀

  1. 草稿草稿生成与最终输出是两个对象层。草稿 A/B/C 可能在目标模型处被拒绝；不能把它们提前写进用户输出。
  2. 首拒绝“连续”是关键。即使后面的草稿偶然也与目标分布相容，C 被拒绝后也不能跳过 C 接受后面的位置。
  3. 重采样D 来自目标模型在首拒绝位置的 residual 分布。它不是把字符串 C 替换成 D；图上保留 C 在拒绝区，D 作为新对象进入提交区。
  4. 全接受全接受不等于白拿一个 token。目标模型仍要在末尾正常采样一次，得到下一轮的起点 token。

不要把 DSpark 画成“字符串比较器”。接受/拒绝发生在目标分布与草稿 token 的概率关系上；本图只画结果分支，不展示真实采样公式与随机数。

性能作用与代价

草稿验证把“每步一个 token”变成“一次目标前向验证多个位置”，但草稿模型本身、目标验证的额外 q 行、拒绝后的重采样以及调度都要计时。只有当接受长度与这些成本的关系合适时，端到端步速才可能改善；本页不把任何接受率或草稿长度换算成加速比例。

机制因果，不是实测。接受率、验证 q 行与步速之间需要 trace / 基准才能定量。

想一想：为什么全接受时还要补一个 token，而不能直接进入下一轮草稿？

验证接受的是“已有草稿位置”的 token；要生成下一个位置，目标模型仍需一次正常采样。补出的 token 成为下一轮上下文的最后一个已提交 token，之后的草稿才有落点。

源码事实分配算例约 6 分钟 · 参数重算

total_q=5，为什么落到 [3,2]

DSpark 的验证预算不是平均切给每个请求。参考实现先给每个序列留 1 个基础 query；剩下的 extra_budget = total_q − num_seqs 按各序列的 confidence 累积乘积做全局排序，再只把入选的额外位置加回每个序列。confidence 是分配信号，不是“必接受”标签。

输入
每请求 confidence 序列、total_q
操作
前缀乘积 → 全局排名 → 计数
输出
每请求 seqlens_q / 验证长度
为什么不能直接取单点
选择第 k 个草稿位置意味着前面的位置也要一起验证；分配单位是一个前缀，而不是孤立位置。
为什么用前缀乘积
每一步 confidence 相乘，表示到该位置为止仍被保留的联合信号；它在同一请求内不递增。
基础 query
每个序列先有 1 个基础 query；额外的入选位置才增加 seqlen_q。
回退
没有性能曲线时退回全 draft；曲线与历史 confidence 都影响 total_q，不能当成静态最优配置。

逐段读 / 先有前缀，后有 rank

  1. 前缀每请求的 confidence 先做累积乘积。同一请求内它不递增；因此某个位置入选时，前面的位置不会更差，分配天然保持前缀形状。
  2. 全局所有请求的前缀放在一起排序。这里用的是全局 flat index；同分按 flat index 稳定处理，不按请求平均切。
  3. 基础 query每条序列最后都加 1。所以 total_q=5 不会直接变成“5 个请求各 5 行”；它先扣掉两个基础 query，再分配 3 个额外位置。
  4. 输入条件total_q 由 confidence 与 decode 性能曲线共同选择。没有曲线时退回全 draft；CPU 新一轮可能看不到 ZOS 最新结果，不能把静态分配当成完整调度。

高 confidence 不是“必接受”。它只决定验证预算的优先顺序。真正的接受/拒绝仍由目标模型验证；本站没有接受率与步速实测，不把 [3,2] 换算成吞吐。

源码事实生产描述边界约 9 分钟 · 编译 → mask → 推进

结构化输出：先把合法空间编译出来

概率采样可能生成不合法 JSON 或语法。事后修补不能保证解码每一步都合法；结构化输出把 schema 编译成语法，维护自动机状态，在采样前把当前状态不允许的候选 mask 掉，再采样并推进状态。约束的是语法续写，不是内容真实。

决策
grammar + 当前 automaton 状态
状态
schema → 编译 → mask → token → 新状态
代价
编译 / mask / 状态推进，不是免费
遇到问题
高概率 token 不一定让 JSON 保持合法；只靠最后修补会破坏已经生成的文本。
谁决定
compiler 把 schema 编成 grammar；matcher 保存状态、trigger 与回退；sampler 每步构造 bitmask。
状态怎么变
合法候选集合由当前自动机状态决定；采样一个 token 后，matcher 推进或回退到下一状态。
边界

mask 只约束“下一步可以是什么”。它不会自动让 boolean 的业务含义正确，也不会让被截断的输出变成完整文档。约束激活前，模型仍可能生成不受语法保护的 token。

性能作用与代价

结构化输出在每步采样前增加 grammar 状态查询与 mask 构造，编译可能发生在请求进入调度前；这些工作改善的是格式约束，不是模型主干的矩阵乘。它可能减少无效重试或后处理，但也会带来编译延迟、mask 张量操作和状态维护，不能直接算成 MFU 收益。

机制因果，不是实测。没有编译耗时、mask 开销或线上格式错误率数据。

想一想：为什么“最后用 JSON parser 修一下”不能替代逐步 mask？

修补发生在 token 已经生成之后，错误结构可能已经改变了后续上下文，且无法保证每次都能补成合法答案。逐步 mask 在采样前就排除不合法续写，让每个解码步骤都有语法定义；但它仍不保证字段内容真实。
