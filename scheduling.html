不要把三层画成同一个框：文本是入口类型，token ID 是模型输入，Sequence 是带状态的请求档案。调度器持有 Sequence；CacheEngine 持有设备上的 KV/state 张量。

性能作用与代价

编码和建档只发生一次，通常不是连续 decode 的主耗时；真正持续的是每步调度、设备下发、KV 增长和输出复制。入口每步复制 RequestOutput，是为了让跨 step 的引用仍然有效，不是免费操作。

源码因果，不是本机测量。没有 tokenizer 或建队耗时数据。

想一想：为什么 LLM 入口不直接保存 GPU KV？

入口负责表达请求与汇总输出，不负责设备内存布局。KV 容量、block 分配和 state 槽位在 worker/cache 侧管理；如果入口也保存一份，状态就会有多个真相。

逐段读 / 首 token 的条件

  1. L470–474q 被剩余预算截断。这里的 seqlen_q 是本次 forward 的 query 行数；cache.num_tokens 是已经缓存的 prompt 前缀。剩余 prompt 按 get_len() - cache.num_tokens 计算，不是 seqlen_q - cache.num_tokens。
  2. L504–511是否允许切块。若本轮被截短且 chunked_prefill 为假，直接不排这个请求；所以关闭后不会凭空出现同一组 4/4/2（固定行 ↗）。
  3. L386–388非最后 chunk 不提交输出。不是跳过 sampling，而是 metadata 的 last_output_token 被置为 -1；sampling 照常执行，sampler 只跳过 SO 状态更新，结果不提交为输出 token。
  4. 第三轮之后首 token 已采样，但还没 forward。此时 len 已加 1，而 cache.num_tokens 仍是 10；下一 decode 的 q=1 才处理这个新 token。

首 token 时刻的准确说法：不是“第一个 chunk 开始”就产出，也不是“prompt 长度除以预算”的纯数学结果；必须看本轮是否覆盖完 prompt、是否被资源条件截断，以及本步是否真的是最后 chunk。

源码事实来自固定 SHA；教学表的 4/4/2 是缩小算例，不是性能测试。

性能作用与代价

chunk 把一次大 prefill 拆成多轮可排的工作；这个版本不支持把 prefill 与 decode 混在同一批，二者安排在不同 step。代价是更多轮调度、launch 和中间状态。首 token 的等待由预算、容量、并行布局和实际覆盖轮次共同决定，不能只用一个“批越大越快”的按钮解释。

源码因果，不是本机测量。页面不给 TTFT 或 MFU 收益百分比。

想一想：预算 4 时，为什么第三轮不是 q=4、k=12？

prompt 只剩 2 个 token 没处理，q 不需要再凑满 4。第三轮 q=2，k = 已缓存 8 + 2 = 10；每个 chunk 都执行 sampling，只是这一轮的 sampling 结果此时才提交为首个输出 token，于是 len=11。下一 decode 的 k=11 来自新 token 还要被 forward。

M03
源码事实两次 all-reduce + 一次本地排班

两个 rank，为什么不能各自决定这一步做什么

NORMAL 引擎在 DP 组里统一本轮做 prefill 还是 decode。第一个投票只回答“想不想”；一个 rank 想，不代表它真能排进块。第二个投票确认“有没有人真的排出 prefill”，然后才决定谁陪跑空 prefill。

逐段读 / 两次决策不能合并

  1. L308–312先看是不是尝试点。ALL 和 ANY 在不同间隔检查，重合时 ANY 优先。不是每个 decode step 都投票；非尝试点直接 _schedule_decode，票一、本地排班、票二都不执行。
  2. L313want 不是“有请求”。还要求 cache 使用率不超过水位，并且队头有可调度的 prefill。两个 rank 的 want 可以不同。
  3. L316–318票一只产生步型。ANY 用 MIN 看是否有人投 0；ALL 用 MIN 看是否全员投 1。它不检查本地 slot 是否真的能排下。
  4. L323–326本地排班可能空手。只有 want 为真才去试；试了也可能因为 slot、block/state 容量或多模态对齐而返回空。
  5. L332–340票二确认“真的有人做”。全组都空手就回 decode，避免 prefill 死循环；若别的 rank 有 prefill，本 rank 返回空 prompt 输出，Worker 接着构造 placeholder 并执行占位 forward。

空 prefill 也是执行：它不是“什么都没发生”。Worker 会用 block_table=[0] 的 placeholder metadata 调主模型（link below），所以看单 rank GPU busy 不能证明有效 token 增加。

placeholder 构造见 model_runner.py:386–403；Worker 分支见 worker.py:120–127。短段摘录不复制完整文件。

性能作用与代价

ALL 追求“全员有活再做”，减少一个 rank 干活、其余 rank 陪跑；ANY 给孤立 rank 一个最迟等待窗口，但会让没排出的 rank 执行 placeholder。两次 all-reduce 和空 prefill 都计入成本，收益要按真实 token、placeholder 占比和全组 step 时间一起看。

源码因果，不是本机测量；不承诺固定 TTFT 改善。

想一想：rank0 想 prefill 但块不够，ANY 会直接让它单独跑吗？

不会。ANY 的票一只让全组进入 prefill 尝试；rank0 本地排班仍可能空手。若全组都空手，票二把它拉回 decode。若另一个 rank 排出了 prefill，rank0 才以空 prefill 陪跑。

逐段读 / 方向和状态

  1. L624–625降序是实现的锚点。输出长的在头端，短的尾端；不要被上一行的旧注释带走。
  2. L629先从尾端执行。r - 1 是当前最短输出请求；本算例先跑 C。
  3. L630–633块不够才找 victim。running[l] 是头端最长输出请求；本算例是 A。释放后继续尝试，而不是无条件执行。这里只是内层 victim 循环；外层 while 处理完当前尾端请求后还会继续，直到 l == r。
  4. L771–780终止分支。状态置 FINISHED_PREEMPTED，释放资源，放进 ignored 输出；输出历史不会再推进。
  5. L781–788重算分支。reset_for_recompute 清运行 cache 状态；waiting.push_front 让它优先重来；释放旧占用。用户已提交的 token 历史仍在 Sequence 中。

不是“删掉最长请求最省事”。选择长输出端作为 victim 是这套比较器的结果，不等于所有实现或所有配置都这样；而且释放块与终止请求是两种不同代价。

ZOS 在途输出被丢弃的条件见 scheduler.hpp:917–924；重算复位见 sequence.hpp:307–310。

性能作用与代价

抢占能让剩余请求继续推进，但不是免费显存：终止降低完成率，重算增加 prefill 计算和尾延迟。头部 victim 释放的块可能更多，代价是长请求的工作被丢弃或重做；应同时看完成吞吐、重算 token 数、抢占次数与尾延迟。

源码因果，不是本机测量。本页不做运行时泄漏或吞吐测试。

想一想：取消请求后，为什么不能马上把它的全部 KV 块分给别人？

取消先改终态，不一定在 cancel 调用里释放块；还要等调度清理、收尾和引用计数归零。若有 clone、共享块或在途旧轮，释放一次只减一层引用。下一单元用三盏灯和引用计数展开。
