性能 / MFU 解释边界

40 层和 5120 宽决定“要做多少主计算”；MoE 稀疏、KV 共享、稀疏索引和 YOCO 减少的是“其中一部分工作”。mHC 融合减少中间读写与 launch，视觉编码增加一次前向。它们都不直接给出 MFU。

配置不能证明吞吐；没有 GPU 实测。若要谈 MFU，必须固定 FLOPs 口径、硬件峰值精度、prefill/decode 窗口、批量与序列长度。

为什么“3 个预测层”不能画成第 40–42 层？

因为它们不在主干 0–39 的顺序里，而是从主干目标层特征出发的侧分支。把 40+3 画成 43 个同构块，会掩盖旁路身份、目标层特征和验证流程。

无 JavaScript 回退：索引选择

  1. layer 20：本层 Q 由 layer 20 hidden 投影；先对全部 12 个合法压缩位置打分，C1=0.90、C7=0.85、C10=0.75 最高，Top-k 按位置排序为 1、7、10。分数产生后才形成候选块 B0/B3，供后续 index 层缩小范围；本层选 Top-k 不受候选限制。
  2. layer 24：主 KV 和 index-K 仍来自 20；候选块 B0/B3 也来自 20；24 只在候选位置 C0、C1、C6、C7 内用本层 index-Q/weights 重新打分，C7=0.90、C1=0.80、C6=0.45，得到 Top-k 1、6、7；最终 attention Q 仍由 24 投影。
  3. layer 26：不重算索引；直接共享 24 的 Top-k 1、6、7；index-K 仍来自 20；最终 Q 仍由 26 投影。
  4. 读取阶段：layer 20 读 C1、C7、C10；layer 24/26 读 C1、C6、C7；三个例子都再读本层 SWA K9、K10、K11。选中的 C 位置才是主 KV 摘要，K 是局部 SWA。两者一起进入核心 attention，输出回本层残差。共享主 KV/index-K 不等于共享上一层 attention 输出。

事件 01 / 05

事实边界：三种模式都保留完整主 KV/index-K，但只有 compact 建立边界并走 _store_yoco_full_kv 的专门 full-hidden/metadata 支路；off 是普通 full 前向，mask 只限制 SWA 可见域。compact 真正减少 consumer query 行，mask 不减行；boundary 清理的是按新布局重建的 candidate 派生缓存，不是擦掉全部缓存。keep 不足时 C++ 会拒绝，本页滑块直接限制在合法范围。

无 JavaScript 回退：YOCO

  1. prefix 层照常算完整 12 行；到 layer 20，三种模式都保留完整主 KV 和 index-K（0–11）。区别是只有 compact 建立 boundary，并触发 _store_yoco_full_kv 的专门 full-hidden/metadata 支路；off/mask 没有这条 compact 专用分叉。
  2. compact：consumer 的 query/后续 norm/MLP 只保留后缀；keep=8 时保留位置 4–11，query 行数 8。早期行不是“把所有 KV 删掉”，只是不再为 consumer 重算。某个早期 chunk 全部落在保留区之前时，compact 仍留一个 placeholder 行。
  3. mask：12 行仍然计算，只把 SWA 可见域裁到保留矩形；矩形外的早期行可见域是空集 ∅，不产生 KV 读取，但行数不减。
  4. off：普通 full query/SWA 前向，12 行都算、不裁可见域，也不做后缀重放。
  5. 可见域统一写成半开区间：W=4 时，位置 4 看 [4,5)；位置 8 看 [5,9)；位置 11 看 [8,12)。mask 的位置 0–3 不是反向区间，而是空集 ∅：下界 max(0, pos-W+1, 保留起点) 被 clamp 到 pos+1，因此没有可见 token。
  6. decode 使用重建后的 SWA ring + 仍然存在的主 KV/index-K。mask 与 compact 共用截断 SWA 可见域，二者相对不截断的 off 都可能有数值差异；compact 额外减少 consumer query 行，mask 保留全部 12 行。

五个不同对象，不能合并成一个“共享 KV”

  • 主 KV按 layer_kv_map alias 到最近 source；20–39 共享 layer 20。
  • index-K自己的映射；24 复用 20 的 key，但仍用自己的 query 打分。
  • Top-k按 index 段共享；24 重新选，25–27 共享 24 的结果。
  • 候选块layer 20 产生；后续 indexer 只在候选块内评分，最终仍受 index_topk 和有效位置限制。
  • SWA每层自己的局部状态；compact 重放的是 consumer 后缀的 SWA，不是主 KV。

一句边界：index-K 共享 ≠ Top-k 共享 ≠ 候选块共享 ≠ attention 输出共享。当前层 Q 仍从当前层 hidden 来；decode 逻辑位置还要转物理 slot。

DeepInfer 短摘录遵循 Apache-2.0；完整文件见固定 commit 链接。

性能 / MFU 解释边界

索引减少核心 attention 要读的 KV 位置；候选块减少 indexer 自己的评分范围；跨层复用减少重复投影/加载；YOCO 减少 consumer query、后续 norm 与 MoE 的行数。成本分别是 indexer、Top-k、地址转换、候选/共享生命周期，以及 compact/gather/full 支路。

短上下文时索引开销占比会更大；“少读位置”或“少算行”不自动等于 MFU 更高。没有实测时不能填吞吐、加速倍数或毫秒。

为什么 layer 26 共享 Top-k，仍不能直接复制 layer 24 的 attention 输出？

共享的是“读哪些位置”的索引，不是 attention 的结果。26 的 Q 来自 26 自己的 hidden，Q 不同、层状态也不同；它仍需用共享位置去读主 KV/SWA，再做本层 attention。

M03
源码事实约 9 分钟 · 3 张并行视图 + 2 条专家路径

同一批卡，分的是不同对象；结果必须回到原 token

DP 分请求/批次，CP 分同一序列的 query 位置，EP 分 routed expert 的物理槽位。它们不是三个依次执行的集群，而是同一组 rank 的三张视图。gate → dispatch → expert → combine 之后，输出仍按原 token 身份和顺序返回；shared expert 另算。EPLB 在固定 physical slot 预算内换副本，不新增模型专家。

并行与专家的三条边界

  • 对象DP 分请求，CP 分同一序列的 query 位置，EP 分 routed expert 的 physical slot；同一组卡可同时属于三种组。
  • 返回dispatch 带原 token 身份/权重；combine 必须回原位置；shared_out 先就绪，作为 combine 的 bias 与 routed 加权一起汇合。输出顺序不能被专家顺序打乱。
  • EPLBlogical 数、physical slot 总数、每 rank slot 数、每 token routed Top-k 数都不变；变的是副本位置、权重字节和两张 map。
  • 低精度1024 个值：BF16 payload 2048 B，FP8 1024 B，FP4 packed 512 B；还有 scale、对齐、padding，不能等同于同比例加速。

一句边界：Mega MoE 不是新专家结构；EPLB 不是新模型专家；生产部署的 CP 选择也不覆盖公开代码的 CP 能力。

性能 / MFU 解释边界

EP 把多个 attention rank 的 expert token 汇成更大的 grouped GEMM batch，机会是减少小 GEMM 浪费；代价是 dispatch/combine 通信、布局转换、symmetric buffer 和专家负载不均。CP 分摊长 prompt 的 query 计算，代价是 all-gather、padding、逆重排与等待。

EPLB 用历史 token 计数代理预测下一步，可能滞后；搬权重本身有时间和 HBM 成本。这里没有 trace、吞吐或 MFU 测量，不能填虚构百分比。

如果 EPLB 把 E0 复制到两张卡，是否等于模型变成了 4 个 logical experts？

不是。logical expert 数仍是 3；physical slot 仍是 4。变化只是 E0 拥有两个副本（P0、P2），E1 的冗余副本退出。gate 仍然选 logical，之后经 map 找可用 physical slot；token 不会被无限制复制给所有副本。

为什么 MoE 动画必须画“返回”，不能停在 expert 计算？

因为 expert 分散在不同 EP rank，dispatch 后每张卡持有的是“发给某个专家的 token 行”，不是完整 batch。combine 要按 handle 把加权结果送回原 token，并加上 shared 输出；少了返回，token 的身份、顺序和最终 hidden 都不成立。
