问题 1 · 缓存 命中为什么还要重放？

Block KV 与 SWA state 是不同对象；命中前缀块不等于继续生成所需状态已就绪。

 问题 2 · 恢复 两类重放各修什么？

encoder 缺 SWA 时只在命中区内重建末尾窗口；consumer 只为 Decode 准备后缀状态，出口不同。

 问题 3 · 控制 谁决定请求去哪？

入口 LB 选实例/rank，Scheduler 选批次/预算，EPLB 搬专家副本；三层。

 问题 4 · 性能 为什么不能泛化？

坐标、配置、并发和计数口径不同；16 并发的官方点是负收益，其余五个为正。

M14
源码布局官方保存策略约 7 分钟 · 对象与生命周期

stored / dropped 是保存范围，不是“磁盘 / 内存”

Block KV 命中只覆盖主 KV 与 indexer K。继续生成还依赖每请求的 SWA 与压缩状态；它们住在 StateBlock 的 stored 与 dropped 两个区。两区都会被 P→D 交接，但跨请求保存只取 stored 区。同一个 state，在“正在使用的 HBM 张量”“P→D 副本”“主机保存副本”里是三种生命周期。

GATE 01 · 128只在 128 的倍数挂接

保存/查询粒度是 128 token；这与“SWA 窗口 128”相关但不是同一个命名空间。

GATE 02 · 最后一个 chunkPrefill 只存最后 chunk

分块 prefill 中途不保存；末尾先保留 1 个 token，再向下对齐到 128 倍数。

GATE 03 · 不足一块不足一个完整 128 单位则不保存

没有完整单位时，本次不产生可挂接的保存点；不能凭 134 或 140 推一个负位置。

GATE 04 · Decode跨 128 边界复制到 replica

结束时取最近完成的设备内副本；主机副本缺失，不等于 Block KV 也缺失。

三个生命周期不要合并：stored/dropped 是保存范围；P→D 传输的是“这次交接需要的两份 state”；跨请求保存的是主机上的副本。字段名、目录名或“已保存”标签都不能单独证明某个字节在磁盘上。

布局与保存范围见 cache_engine.py:221–306；官方保存策略与介质见 Q&A:129–177。官方示例的 20 层 × 134 token × 528 B = 1,415,040 B / 序列属于该快照的 V4.1 配置，不是所有模型常量。

M15
源码事实教学算例约 9 分钟 · 两类重放 + 可调对照

都叫“重放”，修的却不是同一个对象

encoder SWA 缺失恢复，是在 Block KV 命中后补齐继续处理所需的 encoder SWA；decoder/consumer 有界重放，是在 CED/YOCO 路径里只为 Decode 准备 consumer SWA。前者回到“已命中的前缀尾段”，后者只处理提示词末尾的有限后缀；consumer SWA 不进跨请求前缀存储。

共同点
都只重算有限窗口，复用已有 Block KV
不同点

近似边界
不是与完整上下文逐位等价
重放 A · encoder SWA 缺失恢复

Block KV 命中，但 SWA 不在

命中长度先由 Block KV 给出，再检查对应 SWA。若缺失，Block KV 命中范围不变：整段仍复用；只取命中区间末尾 128 token 的 SWA 窗口重建，已命中的 Block KV 原样复用，不重算、不覆盖。

触发
Block KV 命中，但相应 SWA 不可用。
重算
只在已命中范围内重放末尾 128 token 的 encoder SWA，与新 suffix 一起前向。
结果
得到继续处理所需的 encoder SWA；整段原 Block KV 保留。
可见域
位置 i 的 SWA 只看 [max(s, i−127), i]，s 是重放起点。
近似：截断的是 SWA 可见域，不是“把所有 attention 输入截掉”。保留前缀 Block KV 也不代表数值与全量 SWA 逐位相同。
重放 B · decoder / consumer 有界重放

只为 Decode 准备 consumer SWA

CED/YOCO 路径只在 encoder 层做完整 Prefill；consumer 的 Block KV 来自 encoder hidden 的投影。Decode 还需要 consumer SWA，于是只处理提示词末尾有限后缀，不跑全长 consumer Prefill。

触发
需要给 Decode 准备 consumer state，而不想全量重算 consumer 层。
重算
只处理末尾有限后缀；具体保留长度受窗口与回退约束。
结果
供 Decode 使用；consumer SWA 不进入跨请求前缀存储。
公开推荐
README 为默认 V4.1 建议 compact + keep_tokens=140；这是推荐配置，不是 134 的新名字。
不要拿前者的“回退 128”套到后者：consumer 的“140”是推荐保留后缀长度，不是一个跨所有配置的复制常数。
窗口 / 粒度128

SWA 窗口与保存/查询粒度都出现 128，但含义不同。

保存只挂在 128 倍数；命中回退也以一个 128 窗口为单位。不能因为都写 128 就把两者合并。

默认推理 ring134

128 + 6：128 是 SWA 窗口，6 是 max backtracking；inference ring 已经是“窗口 + 最大回退”，不是 134 之外再加 backtracking。

134 不是所有运行配置的常量；kvstore ring 还可再叠加 extra-state。命中上限按 L − 134 只是官方策略的教学例。

README 推荐保留140

默认 V4.1 的 consumer Prefill 推荐保留长度（compact 模式）。

它不是 134 的别名，也不是“复制长度通用常数”；保留长度需满足窗口 + 回退约束。

展开推导：1914、1792、1664 与重放区间分别怎么来？

1. 官方命中上限：L − 134 = 2048 − 134 = 1914。这里的 134 是默认 inference ring：128 窗口 + 6 max backtracking；不是“134 之外再加 backtracking”，kvstore ring 还可另加 extra-state。

2. Block KV 命中必须按 128 对齐；在这个前提下取实际 L1 = 1792（不超过 1914 的 128 倍数）。

3. SWA 可用：Block KV 复用 [0,1792)，SWA 重建 0，suffix 为 [1792,2048)，长度 2048 − 1792 = 256。

4. SWA 缺失：Block KV 仍复用整段 [0,1792)，命中不缩短；只在其中取末尾窗口 [1664,1792) 的 128 token 重建 encoder SWA，suffix 仍是 256。

5. 若 L1=0，没有命中窗口，也不会生成 SWA 重建子区；直接完整处理。短输入、未命中或不足一块都不套用上述减法，不产生负位置。

源码锚点：命中策略见 Q&A:179–191；可见域见 prepare_tensor_input_v4.cpp:149–167；ring 与配置见 cache_engine.py:88–109、environ.py:135–139、README:25。consumer 模式细节见 模型页 YOCO 有界重放。

源码事实配置边界约 6 分钟 · 角色 + flush

三种角色不是任意组合；没有待调度请求也不等于交付完毕

NORMAL 处理 prompt 与 completion，PROMPT 只处理 prompt，COMPLETION 只处理 completion。COMPLETION 没有 Prefill 通道，所以构造 Scheduler 时拒绝 stop_preempted_request=false；它不是等显存不足后再偷偷切到 Prefill。ZOS 的最后一轮还可能留着上一轮 in-flight 状态，入口必须 flush_inflight_reqs 后才退出。

逐段读 / 角色

  1. enum三个值对应三种职责；注释直接写出“prompts / completions”，不能把 PROMPT 当成“先跑 prompt 再自动切 D”。
  2. ZOS默认集合是 NORMAL 与 COMPLETION；PROMPT 默认关闭。默认值可配置，不等于“永远不能开”。
  3. 构造检查COMPLETION 无 Prefill 通道，因此 stop_preempted_request=false 在 Scheduler 构造时被拒绝；见 scheduler.hpp:98–104。

不要把“角色”画成三个进程类。NORMAL / PROMPT / COMPLETION 是引擎工作角色；VE / P / D 是生产部署阶段。两者相关，但不是同一层枚举。

最后一轮收尾 · 同一个 token T 从 sample 到 RequestOutput方法顺序，不是硬件 trace
第 N 轮 · sample T 已采样，event 已记录

普通 ZOS decode 步先下发 forward，再处理上一轮，随后修正长度并 sample 当前轮。sample_end_evt.record() 只是记录，不等于完成。

状态保存 T 留在 prev_step_state

当前轮 state 被保存给下一轮；CPU 侧可能还没拿到 T，RequestOutput 也还没产生。此时“没有新的可调度请求”与“结果已交付”不同。

unfinished=false · 1 先 flush 在途请求

LLM._run_engine 发现没有 unfinished 后，改走 flush_inflight_reqs()；它同步 sample event，并对 prev_step_state 做 post-process，返回最后一批 raw output。

循环内 · 2 clone / 收集，然后 break

对 flush 返回的每个 raw output 执行 RequestOutput.clone，按 request_id 收集；随后才因 not unfinished 跳出循环。clone 在 break 之前。

循环外 · 3 最终 decode → 交付

循环退出后，才按 request_id 排序并做 tokenizer decode，返回最终结果。顺序是 flush → clone/收集 → break → decode，不是 flush 完就立即 decode。

可追踪对象：T 依次经过 sample 完成、在途 state、flush 的 post-process、clone/收集、break 与最终 decode；不要只画“进度条到 100%”。也没有待调度请求时，仍可能有在途结果。

入口循环见 llm.py:174–186；flush 与 post-process 见 worker.py:274–283；worker 步进顺序见 worker.py:113–189；ZOS 顺序细节见 运行时页 ZOS。

判断口诀：角色决定“这个引擎做哪段工作”；ZOS 决定“上一轮后处理能否推迟”；flush 决定“最后还没交付的结果怎么收口”。三者不能用一个“结束”状态概括。

工作点不能泛化的四个原因：① 配置不同（EP/DP、专家数、context、nextn、a）；② 坐标不同（step 时延、每用户吞吐、每卡吞吐、端到端 TTFT）；③ 并发与 batch 改变每步工作量；④ 计数口径不同（benchmark 满接受、τ 折算、DSpark 固定/动态验证）。任意一项换了，就不能把旧点的收益直接搬过去。
性能作用与代价

有界重放减少的是可重算范围，不是把所有前缀工作删掉：Block KV 仍要读，consumer 的 full KV 支路与边界转换仍有成本。动态验证减少低收益的验证 token，但引入置信度调度、GPU 侧重算与元数据校正；收益取决于并发与接受率分布，16 并发的官方退化就是边界。

本页无 GPU 实测；官方图表与 DSpark 表是特定快照的官方描述/估算。MFU、GPU busy 与用户吞吐仍是不同仪表，不能互相替代。

想一想：如果读者只记住“缓存命中就省 prefill”，会漏掉什么？

会漏掉命中长度检查、SWA/consumer state 的可用性、fetch/swap-in 成本、P→D 交接与最后一轮 flush。更稳的说法是：Block KV 命中减少了可复用的前缀块工作，但继续计算所需状态和异步尾部仍需单独满足。

官方 DSpark 表与收益见 Q&A:245–264；可变长度预算见 schedule_mtp_varlen.py:20–97；采样页的 DSpark 机制见 采样与结构。
